Prepared: 27 Nov 2026, updated 28 Nov 2026 (revision 2, after the lead's review of F-01 to F-10), as input to Revision 9 of ASKTD_SPRINT_1_2_STORIES.txt. Until Revision 9 exists, this file is the source for the Stories below. Everything else in the delivery Stories file stays as it is.

## 1. What this file is

One changed Story and thirteen new ones. They record the lead's decisions of 27 and 28 Nov 2026 on the review of the Registry pull request (planning Story Task 1, ASKTD-27).

- Changed: S1-04 (ASKTD-73).
- New: F-01 to F-10. F-01 waits until after the January demo; the others are not placed in a sprint yet.
- New, known limitations that the lead accepted: L-01 to L-03. Each documents a use case; no work is planned.

**Decisions behind these Stories (lead, 27 and 28 Nov 2026).**
1. A central team maintains the Registry and is the only user of the Registry workspace. General users work only in the Chat. The second part of the Registry pull request (F-10) enforces this with one configured group, the Registry group: only its members can open the workspace, to view and to edit.
2. The application creates no table. Until the January demo the table-creation scripts are kept in one folder of the application repository and are applied by hand in the development sandbox. A repository for database changes with Alembic migrations comes when the team moves to the development environment; it is outside the current two months (F-01).
3. The recipes that are defined in code are legacy from the demo. They are not shown in the catalogue and will be retired, and no Story registers them. A Recipe is a record in the Registry.
4. Metadata enters the Registry from the Excel export of Data Compass. A direct connection is not possible today and is automated later.
5. The same export serves the import in SpruceX.
6. SQLite is not allowed: the architecture defines SQL Server only. The Registry pull request removes it from the Registry stores that it adds; F-08 moves every other use to SQL Server and removes the SQLite code completely.
7. For now everyone works on the dbo schema. Real SQL Server tests run there, inside a transaction that they roll back or on rows that they created. They never drop a table and never touch a table outside the Registry. F-09 gives them a database or schema of their own.
8. The Registry pull request is merged in two parts: before the merge only what decides what enters the main branch; the rest in a second pull request, before the catalogue is switched on (F-10).
9. Mock identity is for testing access levels only. It works only in development and is refused in every other environment (F-02).

**How to use this file.** As for the delivery Stories file: the lead reviews it, places it in the agent's workspace and sends the prompt that belongs to it. Sending that prompt is the lead's authorisation.

# Changed Story

## S1-04 — Metadata sync v1: Data Compass and the physical schema into the Registry

asktd-delivery:S1-04

- Sprint candidate: Sprint 1 · Priority: Must · Track: Platform
- Owner: AI engineer, named by the lead; the data engineer supports
- Plan: P04 — Registry and approved relationships for both providers
- Related planning Stories: R1-B (Certify the pilot semantic bundle and intake/binding contracts); Task 1 (Registry and Recipe workspace — S1–S5); Connections (Durable connection profiles and exact Dataset bindings)
- Labels: asktd-delivery, asktd-jan-milestone, asktd-sprint1-candidate
- Team rules: see S1-10 (ASKTD-79)

**User story.** As a Registry maintainer, I want the tables and columns of a data product to enter the Registry from the Data Compass export and from the physical schema through one repeatable import, so that the Registry matches the real tables and nobody types 150 columns by hand.

**Use case.** The three Deposits base tables are in the development sandbox with test data. A Registry maintainer takes the latest export, runs the import in dry-run mode, reads the differences (a column of the export that the table does not have, a column without a description), runs it for real, and sees the three datasets with all their fields in the Registry workspace, beside the datasets that were there before. In SpruceX the maintainer repeats the same steps with the same file and the binding of that environment.

**What to deliver.**
1. An import with two inputs: the Excel export of Data Compass, read as Data Compass produces it, and the physical schema of the same tables in the environment where the import runs. The table name, the column name and the business description come from the export; the data type and the key of each column come from the database. The import writes the source, schema, product group, dataset and field records into the Registry and records the provenance of the run (which file, which date, which environment). The reader of the export sits behind a small interface, so that S2-10 (ASKTD-93) can replace the file with a direct read.
2. A binding for each environment: a small table that names the schema under which each table sits there. The export carries the schema of the source, and in the development sandbox the same tables sit under another schema. The import writes the object identifier of a dataset from the schema and table of this binding, never from the dataset name. A table without a binding stops the import with a clear message.
3. The import adds to the current content of the Registry: every record that the file does not name is carried forward unchanged.
4. A dry-run mode that shows the differences and writes nothing.
5. A difference report: columns found in only one input, type differences, fields without a business definition, columns that have more than one definition in the export, and the data treatment that the export names for each column. The import loads no definition for a column with more than one until a person has chosen one.
6. The business definitions of the export, loaded into a description on the dataset record and a description and business term on the field record. According to the review of 27 Nov 2026, the Registry pull request already adds an empty description to these records, and the import fills it. A business term on the field record is added if it is not there.
7. A rule for what the import owns: the structural facts of a dataset and a field (names, type, key). It fills a business name or description only where there is none, and never replaces one that a person wrote.
8. A guard on the existing seed import script: it stops with a message when the latest Registry version holds records that the seed files do not have.
9. A `sync-metadata` skill in the form that S1-10 (ASKTD-79) set up, which runs the import in dry-run mode and summarises the differences.
10. The governed Registry settings switched on in the development sandbox, with a note on what changes in behaviour.

**Done when.**
- After one run in the development sandbox, the Registry workspace lists the three Deposits datasets with all their columns beside the datasets that were there before, and the provenance of the run names the file, its date and the environment.
- The object identifier of each of the three datasets equals the schema and table of the binding.
- A second run with unchanged inputs publishes no new Registry version.
- A test shows that relationships, Metrics, Recipes and the datasets that the file does not name are identical before and after a run.
- The BSA has received the list of fields without a business definition and of columns with more than one.
- With the governed Registry settings on in the development sandbox, the existing demo questions still answer. Any failure is recorded as a defect with its steps, not worked around.

**Not in scope.** Relationships (S2-01 = ASKTD-82); the impact report (S2-06 = ASKTD-91); any change to Metrics or Recipes; tables other than the three Deposits base tables; a scheduled run that publishes without a person's review (the plan excludes an automatic catalogue sync from the pilot — planning Story R1-B); a direct connection to Data Compass (S2-10 = ASKTD-93); storing the classification columns of the export in the Registry; running the import in SpruceX, which the demo path does once the import is finished, with the same file and the binding of that environment.

**Depends on.** The Excel export of Data Compass for the Deposits data product; the manual copy in the development sandbox; the merge of the Registry pull request (planning Story Task 1, ASKTD-27), because the import writes through the Registry repository that it adds.

**Notes for the developer.** The real export is not committed to the repository: it is given to the import at run time, and tests use a small synthetic file with the same columns. SQLite is not allowed: a test that needs a database runs on SQL Server in the development sandbox, for now on the dbo schema, inside a transaction that it rolls back or deleting only the rows that it created. It never drops a table and never touches a Deposits table. The work is built on a branch of its own and merged as its own pull request. Before deliverable 10: a comparison of 27 Nov 2026 found that with the governed Registry settings forced on, 8 of 22 test fixtures fail on the main branch as well, because they create no evidence files. Find out what the settings need before they are switched on.

**Copilot prompt.**
```text
Build metadata import v1 for the Deposits data product. Inputs: the Excel export of Data Compass, given as a file path at run time, and the physical schema of the three Deposits base tables in the development sandbox. Target: the Registry, through its own repository (registry_catalog/sql_repository.py); do not write to its tables directly. Read registry_contract.py first to learn the record types, and the existing importer script to see what can be reused. Read the workbook with a library that the project already has; if there is none, ask before adding one.

From the export read the table name, the column name and the business description. Read the data type and the key of each column from the database. Read the schema of each table in this environment from a small binding file, and write the object identifier of the dataset from that schema and the table name, never from the dataset name. Stop with a clear message when a table has no binding.

Create or update the Source, Schema, ProductGroup, Dataset and Field records, and record the provenance of the run (which file, which date, which environment). Put the reader of the export behind a small interface: a later Story reads the same content from another location. Where the two inputs disagree (a missing column, a different type), keep the physical schema and list the difference in a report. The report also lists the data treatment that the export names for each column.

Add a description to the dataset record and a description and a business term to the field record, and fill them from the export. Where a column has more than one definition, load none and list the column in the report. The import owns only structural facts (names, type, key): it fills a business name or description where there is none and never replaces one that a person wrote. Carry every other record of the current snapshot forward unchanged, including the datasets that the file does not name: never create, edit or drop relationships, Metrics or Recipes, and do not rebuild the snapshot from the seed files.

The import needs a dry-run mode that prints the differences without writing. An applied run publishes one new Registry version; a run without changes publishes nothing. Do not commit the real export: tests use a small synthetic file with the same columns. Do not use SQLite: a test that needs a database runs on SQL Server in the development sandbox, on the dbo schema, inside a transaction that it rolls back; it never drops a table and never touches a Deposits table. Add tests for: first load beside existing datasets, rerun without change, added column, removed column, a table without a binding.
```

**Terms.**
- Track: demo path is work the January demo depends on; platform is work for the next data products, and it gives way when the demo path needs people.
- Recipe: a reviewed definition of how one kind of question is calculated.
- Registry: the governed catalogue of datasets, fields, relationships and other definitions, stored in the database.
- Registry version: one published, numbered state of the Registry.
- Governed Registry settings: the settings that make the application read the Registry at run time.
- Binding: the record of where a dataset physically sits in one environment: its schema and table.
- Data treatment: what the export says is done to a column in a copy of the data, for example rounded, masked or removed.
- Development sandbox: the environment where the team builds; it has model access and the manual copy.
- SpruceX: a separate environment with access to production data; the real-data tests and the demo run there.
- Manual copy: the copy of the Deposits tables in the development sandbox, for development only.
- Data Compass: the enterprise catalogue in which a data product is registered. It can export its content as an Excel file.

## F-01 — A repository for database changes with Alembic migrations (after the January demo)

asktd-delivery:F-01

- Sprint candidate: after the January demo · Priority: Later · Track: Platform
- Owner: to be named by the lead
- Plan: none (team enabler)
- Related planning Stories: Task 1 (Registry and Recipe workspace — S1–S5)
- Labels: asktd-delivery, asktd-later-candidate
- Team rules: see S1-10 (ASKTD-79)

**Not now.** This Story is outside the deliverables of the current two months. No current Story waits for it. Until it starts, the Registry table scripts stay in the scripts folder of the application repository and are applied by hand in the development sandbox.

**User story.** As the team, we want every database change to go through a repository of its own with versioned Alembic migrations, so that each environment can be brought to a known version of the schema in a repeatable way and the application never creates a table.

**Use case.** Until the January demo the team works in the development sandbox on the dbo schema, and the Registry tables are created there by hand from the scripts folder. When the team moves to the development environment, that environment and later ones have to reach the same schema, and the team needs to see which change ran where.

**What to deliver.**
1. A repository for database changes, separate from the application repository, with Alembic migrations for SQL Server.
2. The scripts of the scripts folder turned into its first migrations, and the folder removed from the application repository.
3. The way a migration is applied in each environment, with its approval, and the migration version of each environment visible.
4. A change that drops a table or deletes data is never applied by the route alone: it needs a named reason and a person's approval.

**Done when.**
- The development environment is brought to the current schema by the migrations, and a second run changes nothing.
- The application starts there with the Registry stages on and finds its tables.
- The migration version of each environment can be read.

**Not in scope.** Application code; the tables of a data product; SpruceX, until the route is agreed for it.

**Depends on.** The move to the development environment; the scripts folder from the Registry pull request (planning Story Task 1, ASKTD-27).

**Copilot prompt.**
```text
In the repository for database changes, set up Alembic for SQL Server. Turn each table-creation script of the Registry scripts folder into one migration, in the order that the folder's README gives, and check that upgrading an empty database gives the same tables, indexes and constraints as the scripts. Do not turn the table-dropping script into a migration. Run it only against the environment that the lead names.
```

**Terms.**
- Alembic: a tool that keeps database changes as numbered migrations and records in the database which of them ran.
- Migration: one numbered, repeatable change to the database schema.
- Development environment: the environment that the team moves to after the development sandbox. It is not the development sandbox.
- Development sandbox: the environment where the team builds today.

## F-02 — Allow mock identity only in development

asktd-delivery:F-02

- Sprint candidate: not placed · Priority: Should · Track: Platform
- Owner: to be named by the lead

- Related planning Stories: ACCESS-01 (Qualify the selected effective-access contract)
- Labels: asktd-delivery, asktd-unscheduled

**User story.** As the lead, I want mock identity to work only in development, so that the team can test access levels easily and no other environment accepts an identity that the caller writes into a header.

**Use case.** The team tests access levels by sending a user and groups in request headers instead of signing in as several real users. This mock identity is for testing only. The review of the Registry pull request found that a hosted process labelled as development accepts it, which is intended. It did not confirm that every other environment refuses it.

**What to deliver.**
1. Mock identity is accepted only when the environment is development. Every other environment refuses it at start-up with a clear message, and so does a process whose environment label is missing or unknown.
2. A test for each refusal, and a test that access-level testing in development still works.
3. A short note in the runtime guide: what mock identity is for and where it works.

**Done when.**
- A start with mock identity outside development, or without an environment label, fails with a clear message.
- In development the team can still test access levels with mock identity.

**Not in scope.** The real sign-in; the access rules themselves.

**Depends on.** Nothing. It has to be finished before the application runs in any environment other than development, for example SpruceX.

**Copilot prompt.**
```text
Read how the application decides whether mock identity is allowed (the review names config.py). Allow it only when the environment is development, and refuse it with a clear start-up message in every other environment and when the environment label is missing or unknown. Add a test for each refusal and a test that mock identity still works in development. Do not change the real sign-in path.
```

**Terms.**
- Mock identity: a testing mode in which the application takes the user and the groups from request headers instead of a signed token.

## F-03 — Use the dataset binding in the access check

asktd-delivery:F-03

- Sprint candidate: not placed · Priority: Must · Track: Platform
- Owner: to be named by the lead
- Plan: P02 — Application access and qualified source routes
- Related planning Stories: Connections (Durable connection profiles and exact Dataset bindings); ACCESS-01 (Qualify the selected effective-access contract)
- Labels: asktd-delivery, asktd-unscheduled
- Team rules: see S1-10 (ASKTD-79)

**User story.** As the owner of the access rules, I want the access check to use the recorded binding of a dataset, so that a grant matches exactly the table it names.

**Use case.** While Deposits data moves from Synapse to Databricks, the same table name exists in two places. Today the access check takes the dataset name as the table name: a grant written with the full name may not match, and two tables with the same name count as one.

**What to deliver.**
1. The access check reads the object identifier of the dataset as the import of S1-04 (ASKTD-73) wrote it from the binding. It never derives the table from the dataset name.
2. A dataset without a binding, and two datasets whose bindings name the same table, are refused with a clear message instead of being matched by a guess.
3. Tests for a grant written with the full name, a missing binding, and two tables with the same name under different schemas.

**Done when.**
- The three tests pass, and no access is granted because two names look alike.
- In the development sandbox a user with the grant sees the three Deposits datasets, and a user without it does not.

**Not in scope.** The Databricks name of a dataset, which S2-08 (ASKTD-87) adds as one more binding; connection profiles (planning Story Connections, ASKTD-20).

**Depends on.** S1-04 (ASKTD-73), which writes the binding.

**Copilot prompt.**
```text
Find where the application compares a dataset with the objects that a user may read (the review names available_data/registry_contract.py and authorization_identifiers.py). Today the dataset name stands in for the table. Change the comparison so that it uses the object identifier that the metadata import writes from the binding. Refuse a dataset without a binding, and a binding that two datasets share, with a clear message. Add tests for a grant with a full name, a missing binding and two tables with the same name under different schemas. Do not change what a user without any grant sees.
```

**Terms.**
- Binding: the record of where a dataset physically sits in one environment: its schema and table.
- Grant: the entry that allows a user or group to read one table.
- Provider: the engine that runs a query: SQL Server or Databricks.

## F-04 — Show the state of each field mapping in the catalogue

asktd-delivery:F-04

- Sprint candidate: not placed · Priority: Later · Track: Platform
- Owner: to be named by the lead
- Plan: P04 — Registry and approved relationships for both providers
- Related planning Stories: Task 1 (Registry and Recipe workspace — S1–S5); R1-B (Certify the pilot semantic bundle and intake/binding contracts)
- Labels: asktd-delivery, asktd-unscheduled
- Team rules: see S1-10 (ASKTD-79)

**User story.** As a Registry maintainer, I want the catalogue to say whether the mapping of a field to its real column was checked, so that an unchecked mapping does not look like missing data.

**Use case.** After an import a maintainer opens a dataset. Some fields were found in the real table with the same type, one was not found, and one is hidden for this user. Today all three look the same: "no data".

**What to deliver.**
1. One state for each outcome in the answer of the catalogue: verified, not verified yet, not found, hidden for this user, and no mapping.
2. The import of S1-04 (ASKTD-73) sets "verified" where its comparison found the column with the same type, and "not found" where it did not.
3. The screen shows the state beside the field.

**Done when.**
- Tests with controlled data tell the five states apart.
- After an import in the development sandbox, the fields of the three Deposits datasets show "verified" where the column exists.

**Not in scope.** The first part of the same finding, which the second part of the Registry pull request (F-10) closes: the answer of the catalogue derives whether fields are available from the loaded records.

**Depends on.** S1-04 (ASKTD-73).

**Copilot prompt.**
```text
Read how the catalogue answer describes a field and its physical mapping (the review names registry_catalog/routes.py and api_models.py). Add one typed state for the mapping of a field: verified, not verified yet, not found, hidden for this user, no mapping. Let the metadata import set verified or not found from its comparison with the real table. Show the state in the field list of the Registry screen, following the pattern of the existing columns. Add tests with controlled data for each state.
```

**Terms.**
- Mapping: the link between a field of the Registry and a column of a real table.
- Registry: the governed catalogue of datasets, fields, relationships and other definitions.

## L-01 — The Registry version shows that hidden data changed

asktd-delivery:L-01

- Sprint candidate: none · Priority: Later · Track: Platform
- Owner: none while it is accepted
- Plan: P04 — Registry and approved relationships for both providers
- Related planning Stories: Task 1 (Registry and Recipe workspace — S1–S5)
- Labels: asktd-delivery, asktd-known-limitation
- Team rules: see S1-10 (ASKTD-79)

**Use case.** A user who may see only a part of the catalogue notices that the Registry version changed although nothing visible changed. The user learns that something hidden exists and changed, and when. The change itself does not appear in the history that this user sees.

**Accepted because** only the members of the Registry group can open the Registry workspace, and they are the central team that maintains the Registry. General users work only in the Chat.

**Starts to matter when** a group with partial access gets the Registry workspace.

**Fix, if it is taken up.** Compute the version in the answer from the records that the user may see, or return a value that stays the same while the visible records do not change.

**Done when, if it is taken up.** A test changes only hidden data, and the answer for the user with partial access stays identical.

**Terms.**
- Registry version: one published, numbered state of the Registry.

## L-02 — A page token outlives a workflow event or a publication

asktd-delivery:L-02

- Sprint candidate: none · Priority: Later · Track: Platform
- Owner: none while it is accepted
- Plan: P04 — Registry and approved relationships for both providers
- Related planning Stories: Task 1 (Registry and Recipe workspace — S1–S5)
- Labels: asktd-delivery, asktd-known-limitation
- Team rules: see S1-10 (ASKTD-79)

**Use case.** While a maintainer pages through a list, somebody approves or publishes something that does not change the displayed data. The old page token still works, and the list is slightly behind until the page is opened again.

**Accepted because** only the members of the Registry group can open the Registry workspace, and the displayed data is the same.

**Done when, if it is taken up.** A change of only one of these two numbers makes an older token invalid, in two tests.

**Terms.**
- Page token: the value that the catalogue returns with one page and expects with the request for the next.
