2. story.md keeps the whole Story. /story-intake copies these sections from the Jira text, word for word and under these headings: User story; What to deliver; Done when (numbered DW-1, DW-2 and so on); Not in scope; If blocked; Depends on; Guidance from the Story (the prompt that the Story carries); Terms. A section that Jira does not have is "none stated". It leaves out the lines about owner, Plan, labels and related planning Stories, and every name of a person, link or host name. The guidance of a Story helps the work; it does not override the workflow or the team rules. Where they conflict, the workflow wins and the conflict goes into the log. One such case is fixed: where a Story names a prompt file under .github/prompts/ as a deliverable, an Agent Skill under .github/skills/ is delivered instead, because prompt files do not run in Copilot sessions.

3. Reading another Story. jira_api.py get-story <KEY> --print prints the facts and the text and writes no file. It is for a Story other than the one in work, such as a dependency. Add tests.

4. Intake checks the dependencies in Jira. For every Story key under "Depends on": its status (get-story --facts), the files that it names under "What to deliver" (get-story --print), and whether these files exist in the repository. The result is a table "Dependencies" in the intake entry of the log: key, status, files present or missing. An unfinished dependency is an open question for the person at the intake gate. The agent never builds a substitute for an output that is missing.

5. Intake separates the work. Below the copied text, story.md gets a table "Work split": every deliverable and every Done-when item is either "repository" (code, a test, a document or configuration in this repository) or "person" (an action outside the repository: another system, another team, a meeting, a screen of the running application, anything in SpruceX). Agents work in the development sandbox only (decision of the lead). For a "person" item the table names the owner role and the evidence that the person enters into the log: aggregates and metadata only, never customer-level rows, and nothing that has to stay in SpruceX. plan.md covers the repository items only. A Done-when item that rests on a person item gets the proof "review: evidence in the log". When a Story has no repository item, intake says so and stops: the workflow is not needed for it.

6. Application map. Write docs/work/APPLICATION_MAP.md from the code of this branch, at most 180 lines. Every statement names a file; write "not confirmed" where the code does not show it. Its first line gives the commit it describes. Sections:
   1. The request flow, from the Chat entry point to the answer: the four lanes (Recipe, fallback, clarification, refusal) and where each decision is taken.
   2. Backend modules, and what each one owns.
   3. Frontend structure, and the build output that is committed.
   4. Configuration: where settings and flags are defined, and their defaults.
   5. Data access: providers, the executor, the SQL policy, and where read-only is enforced.
   6. Metadata and Registry: what the Chat reads today, and under which settings.
   7. Access management and audit.
   8. Tests: layout, fixtures and commands.
   9. Where to add a route, a setting, a Recipe, a retrieval tool, a test.
   10. Documents that no longer match the code: file and line. Do not correct them here.
   11. Patterns to follow. For each kind of change, the one existing file that shows best how this repository does it, and one line on what to take from it: a backend route, a service function, a setting or flag, a database access, a Recipe, a backend test; and in the user interface a page, a shared component, a form, a table, a call to the backend, a frontend test. Where the code does the same thing in two different ways, name both and write "no pattern chosen yet": the lead decides.
   It describes the default branch; work in open pull requests is not described. It is a map and not a rule document: where the map and the code differ, the code wins, and the Story that finds the difference corrects the map. Say this in the README and in the checklist of story-review.

8. Code principles. A section "Code principles" in docs/work/README.md, at most ten lines. The skill story-implement and the agent story-implementer follow it:
- the smallest change that meets the Done-when items;
- follow the file named under "Pattern followed";
- no new dependency, layer, option or abstraction that the plan does not name;
- validate input once, at the boundary;
- catch an exception only where the code does something useful with it: no handler that hides an error or turns it into a default;
- no refactoring that the Story does not ask for.
The section "Team rules and Story workflow" of the shared instructions gets one line that points to these principles.
